## 1단계 — 무손실 저장과 중복 작업 제거

- 길이가 긴 숫자 배열을 IEEE-754 Float64 이진 포장 후 gzip으로 저장한다. 재고·기후 캐시·관측 숫자를 양자화하지 않는다. 모델 저장 v11·대기 v6, 64MiB 원문·20MiB 압축 한도, 계정 충돌·리비전 규칙은 유지한다.
- 새 코드는 이전 gzip JSON과 IndexedDB 객체 저장을 계속 읽는다. 새 형식은 이진 전송 포장 버전이며 이전 앱이 새 포장을 읽는 역방향 호환성까지 제공하지는 않는다.
- 현재 v11 상태에 불필요한 Float32 변환·깊은 대기 이중 복사를 줄였다. 음수 반올림 수리가 필요한 저장은 기존 마이그레이션 경로를 사용한다.
- 정산할 명령·낙하가 없는 세션은 그림자 기후 계산기를 새로 생성하지 않고, 저장마다 활성 행성을 두 번 정산하던 경로를 한 번으로 합쳤다.

같은 조건(2,562셀 목성, 14×1/30게임초 진행, 각 모드 4개씩, 관측 이력 제외)의 결과:

## 2단계 — 비동기 저장 준비·분할 실행·전체 관측 이력

- 자동 저장의 검증·마이그레이션을 별도 Worker로 보낸다. 메시지는 복사한 무손실 이진 버퍼로 전달하며 살아 있는 계산 버퍼를 detach하지 않는다. 검증 오류는 거부하고, Worker 생성·통신 실패는 보존한 캡처로 기존 검사 경로에 복구한다.
- 저장을 기다리는 동안의 새 물리 단계와 관측 표본이 과거 저장 장부에 섞이지 않게, 세계와 telemetry 에너지·이력을 같은 완료 시점에서 고정한다.
- 숫자 포장·해제는 짧은 작업으로 나눠 UI 스케줄러에 실행 기회를 준다. 변경 없는 정지 상태는 반복 저장을 생략하고, 0시간 편집 등 상태 revision과 환경·회전·재고·과제·관측 메타데이터가 달라지면 다시 저장한다. 원격 동기화나 IDB의 실제 프레임 지연은 아직 브라우저에서 측정하지 못했다.
- Float64의 바이트 순서를 무손실 재배열하고 관측 숫자 열의 키를 공유한다. 첫 이진 포장(v1)과 JSON 읽기를 유지한 v2 전송 포장이다. 스냅샷 모델 형식·재고·캐시는 바꾸지 않는다.
- 8개 진행한 목성은 gzip 약 **12,564,200B**로 저장됐다(같은 14단계 조건, 메타데이터 길이에 따라 수십 바이트 차이). 이전 21,306,431B 대비 약 41% 감소했다.
- **각 행성 2,048개 표본 × 8행성**의 최대 보관 이력을 넣은 합성 저장도 gzip **13,919,879B**, 원문 이진 포장 **52,340,104B**로 기존 한도 이내였다. 전체 숫자·null·이력 JSON 비교와 저장 후 정확한 물리 재개가 통과했다. 이력은 재현 가능한 합성 값이며, 장기 기후 계산을 2,048게임초 실행했다는 뜻은 아니다. 임의의 고엔트로피 유효 데이터 전체에 대해 압축 한도를 보장하는 결과도 아니다.
- Worker 캡처·실패 복구·잘못된 입력 거부·장부 고정·이전 포장과 IDB 호환 등 **27개 검사**, 확장한 저장 코덱 **6개 검사**, TypeScript·버전 검사가 통과했다. 실제 브라우저 Worker/GPU는 미검증이다.

증거: `stage2-save-metrics.json`, `stage2-tests.json`, `max-history-tests.json`, `max-history-metrics.json`.

## 3단계 — 대기·공통 열역학 처리량

- 에너지·열용량에서 실제 0계수만 건너뛰고 나머지 항의 순서를 유지한다. 수송 중 바뀌지 않는 층 에너지를 해당 단계에서 캐시하고 commit 뒤 다시 계산한다. 깊은 대기는 고정 접평면 기하·열압력 값을 공유하고 벡터/흐름 임시 객체를 재사용 버퍼로 바꾼다.
- 반응 데이터의 최저 점화 온도 이하에서는 불필요한 반응 경로 생성을 줄이되, 기존 무반응 에너지 역산과 운동량 반올림을 유지한다. 시간 간격·CFL·법칙·재고·복사 캐시 갱신 기준은 바꾸지 않는다.

구현 직전과 같은 하네스의 정상 8단계 평균(각 조건 독립 초기화, 준비 2단계):

| 2,562셀 조건 | 변경 전 | 변경 후 | 시간 감소 |
| --- | ---: | ---: | ---: |
| 건조·질소 | 160.31ms | 131.52ms | 18.0% |
| 젖은 해안 | 170.48ms | 139.01ms | 18.5% |
| 메탄·중력 0.3 | 168.34ms | 135.01ms | 19.8% |
| 목성 | 219.44ms | 183.89ms | 16.2% |
| 기후 끈 진단 대조 | 21.38ms | 18.51ms | 13.4% |

162·642셀을 포함한 **7조건 모두** 유효 상태·기후 재고/온도/바람/캐시·에너지/탈출/섭식 진단 해시가 변경 전과 일치했다. 비활성 대기의 초기 빈 버퍼는 물리 상태 해시에서 제외한다. 기존 24단계 공급·가열 감사의 dry/wet/methane 해시도 완전히 일치했다. 연소·산소·상승기류·보존·저온·깊은 대기 등 **73개 검사**가 통과했다.

이것은 CPU 소스 실행의 개선이다. 여전히 1× 목표의 33.33ms보다 길며 실제 브라우저 FPS·GPU 처리량을 달성했다고 해석하지 않는다. 측정 표본이 작고 장기 상태의 CFL 변화는 별도 검증 대상이다.

## 4단계 — 배경 상태 게시·미사용 대기 메모리·제한 동시 실행

- 실제 앱의 비동기 배경 경로는 완료 시점의 typed 상태를 보존하고, 일반 저장 배열을 읽을 때 한 번만 변환한다. 이후 솔버가 버퍼를 재사용해도 이전 게시 상태와 시간이 유지된다. 오프라인 동기 API의 기존 참조 갱신 계약은 보존했다.
- 일반/깊은 대기를 실제로 사용할 때만 할당하고, 미초기화 대기 체크포인트는 빈 버퍼·메타데이터로 표현한다. 상태 확인·진단만으로 미사용 대기를 만들지 않는다. 그을음 복사 2개 배열도 transfer 목록에 넣었다.
- 배경 작업은 최대 2개씩, 활성 계산과 독립적으로 실행한다. 오류가 있어도 현재 묶음의 모든 작업이 끝난 뒤 반환한다. 각 행성의 시간 단계·법칙·완료 상태와 실패 시 재시도는 유지한다.

2,562셀 젖은 해안의 일반 기후 snapshot은 14.42ms, 지연 typed 캡처는 0.30ms였다. CPU Solver 고유 typed 버퍼는 일반 대기 21.66→14.84MiB, 목성 21.66→13.21MiB, 기후를 끈 대조군 21.66→3.95MiB였다. JS 전체 힙·GPU 메모리나 누수를 측정한 값은 아니다. 이 변경 뒤에도 7조건의 유효 상태 해시가 변경 전과 일치했다.

`benchmark-workers.mjs`는 실제 Node worker_threads에 브라우저 솔버 번들을 CPU 강제로 올려 실제 메시지·버퍼 전달을 검증한다. Mac UI나 GPU에는 접근하지 않는다. wet·Jupiter의 직접 CPU와 Worker 결과 및 3행성 순차/동시 실행의 완료 결과가 모두 정확히 일치했다. 이벤트 루프 간격과 처리량의 수치는 동봉 `node-workers.json`을 따른다. 이 값은 브라우저 프레임·실기 GPU 검증을 대신하지 않는다.

이전 오프라인 동기 참조 계약을 검출한 2개 회귀를 수정한 뒤 관련 30개 검사(배경·Worker·장부·참조)가 통과했다. 그 외 배경 광범위 실행에서 통과한 보존·저장·행성 검사와 함께 최종 전체 회귀를 다시 수행할 예정이다.
