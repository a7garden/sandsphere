## 완료 기준

- 기존 sand400/water1000 재현 입력의 질량 오차를 기존 절대 허용치 0.002 kg 이내로 해결한다. 허용치를 늘리거나 입력 재고를 줄이지 않는다.

- 큰 재고 장시간 실행과 중간 JSON 저장 재개, CPU/Worker/GPU 비교를 검사한다.
- localStorage 용량보다 큰 저장을 생산 저장 경로로 기록하고 다시 읽는다. 기존 저장을 읽고, 실패·중단·동시 저장에서 마지막 정상 저장을 보존한다.
- 전체 회귀·빌드·버전 검사 및 실제 앱 저장 재개를 확인한다. 새로고침/종료의 보장 범위와 브라우저 저장소 자체의 실패는 구분한다.

## 구현 구조

지표 물질은 각 계산 단계에서 Float64 재고로 복원한다. 화면·GPU 버퍼의
Float32 투영값과 그 값에 담기지 않는 셀별·물질별 `surfaceMassCarry`를 함께
저장한다. 잔여량은 총합을 맞추기 위한 전역 보정이 아니라 다음 이동·반응·
회수·삭제·운석·에너지 계산에 쓰이는 해당 재료의 실제 재고다. 층상 대기의
별도 재고는 기존 Float64가 정본이며, 그 표시용 합계에 잔여량을 중복 더하지 않는다.

CPU와 WebGPU는 같은 호스트 물질 수송을 사용한다. GPU 계산의 Float32
결과로 물리 재고를 덮지 않는다. 따라서 이 변경은 정밀도·동등성 개선이며
GPU 처리량 개선을 주장하지 않는다. 렌더링은 기존 Float32 투영을 사용하고,
수지·CSV·관측 물질 합계는 정밀 재고를 읽는다.

간소화 기후 v6·층상 기후 v7에 물질 잔여량을 저장한다. 바깥 저장 v11과
셀 폭 40은 유지한다. 기존 저장에 잔여량이 없으면 0으로 시작하며,
당시 저장된 재고를 재해석해 임의의 물질을 추가하지 않는다. 새 저장을
이전 앱 버전이 읽을 수 있다는 역방향 호환성은 보장하지 않는다.

브라우저의 큰 저장은 기존 IndexedDB `sandsphere` 데이터베이스를 사용한다.
종료 때 전체 JSON을 localStorage에 복제하지 않는다. 저장 시점부터 열린
트랜잭션에 행성·관측 복구 정보·기존 저장 인계 표시를 원자적으로 기록한다.
localStorage의 기존 저장 원문은 보존하고, 인계된 정확한 저장만 다시 선택하지
않도록 한다. 새로운 자동 저장이 완료된 뒤 오래된 요청이 덮어쓰지 않도록 한다.

브라우저가 저장 커밋 전에 강제로 종료되거나 IndexedDB 자체의 용량·권한이
부족하면 최신 미완료 저장을 보장할 수 없다. 실패는 이전 정상 저장을 훼손하지
않아야 하며, 완료되지 않은 체크포인트의 알림도 가능한 범위에서 남긴다.
이는 localStorage의 작은 용량 제한 해결과 구별되는 저장 장치의 실패 범위다.

## 저장 검증 진행과 실패 보존

실제 브라우저에서 2,562셀 행성 8개, JSON 50,638,914 bytes를 기록·복원했다.
localStorage에 시험용 데이터만 채워 실제 QuotaExceededError를 발생시킨
상태에서도 IndexedDB 저장과 정확한 복원이 통과했다. 트랜잭션 중단,
최신/과거 쓰기 경쟁, 호출 뒤 값 변경, 기존 저장 보존·인계, 명시적 저장본
교체와 오래된 창의 뒤늦은 저장, 오래된 정리 작업의 경쟁까지 9건 통과했다.

이 과정에서 과거 요청의 의도적 중단을 오류로 처리하던 문제와, 체크포인트
정리가 세대 메타데이터까지 삭제하던 문제를 재현·수정했다. 실패 기록은
`persistence-initial-failure.txt`와 `persistence-generation-failure.txt`에 남겼다.
종료하는 문서에서 시작한 50 MB IndexedDB 쓰기는 일반 pagehide뿐 아니라
명시적 commit 후에도 다음 페이지에서 최신본을 읽지 못했다. 이 결과는
`persistence-pagehide-failure.txt`, `persistence-explicit-commit-pagehide-failure.txt`에
보존하며, 종료 시점 경로를 완료 판정하기 전에 별도 수정·재검증한다.


### 종료 시점 저장 수정 및 최종 브라우저 결과

문서 수명에 묶인 쓰기의 실패를 해결하기 위해 저장 전용 Service Worker를
사용한다. 페이지 종료 전에 메시지의 데이터를 전달하고, 워커는
`message.waitUntil()`로 실제 IndexedDB 커밋을 완료한다. 시작 시 준비 메시지는
이미 받은 쓰기가 끝날 때까지 기다린다. 워커는 좁은 전용 scope를 가지며
fetch 가로채기·캐시·페이지 제어를 하지 않는다. 워커가 지원되지 않을 때에는
저장되지 않은 실제 변경이 있으면 종료 경고를 제공한다.

프로덕션 빌드의 실제 앱 재시작에서는 42초 상태와 투입한 물이 복원됐지만
완료되지 않은 저장 알림이 남는 경쟁도 발견했다. 숨김 이벤트가 워커 체크포인트를
보낸 다음 같은 상태를 더 새 시각의 일반 자동 저장으로 다시 요청했고,
그 문서의 쓰기만 종료 때 취소되면서 pending 표시가 앞선 정상 커밋보다
새로 남는 경우였다. 숨김 이벤트는 워커 경로만 사용하며, 이미 기다리던
자동 저장도 재개 시 문서가 숨겨졌으면 워커로 넘기도록 `main.ts`만 수정했다.
물리 상태·저장 스키마와 실제 실패 알림의 판정 기준은 바꾸지 않았다.

최종 실제 브라우저 검증은 워커 활성화를 포함한 10건 전부 통과했다.
동일한 50,638,914 bytes를 pagehide 때 처음 저장한 뒤 실제 링크로 페이지를
이동했다. 새 페이지에서 baseline 200 대신 최신 저장 201을 읽었고, 전체 JSON의
SHA-256 `f70383f601bac001ee1e82add516cc7107059138937d348c94ca6ccb8cacc8cc`가
정확히 일치했다. 근거는 `persistence-worker-pass.txt`,
`persistence-worker-pagehide-pass.txt`, `persistence-worker-pagehide.png`다.
이전 실패는 중간 구현의 실패로 남겼으며 같은 시나리오의 성공으로 교체 검증했다.

운영체제 강제 종료·저장 장치 장애·IndexedDB 전체 용량 부족까지 최신 미완료
상태를 보장하지 않는다. 이번 검증은 실제 일반 페이지 이동, 기존 저장 호환,
localStorage 용량 초과, 트랜잭션 실패와 동시 쓰기 경쟁의 범위다.
